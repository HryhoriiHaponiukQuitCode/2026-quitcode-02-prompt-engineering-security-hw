# Документування модуля

## Роль

Технічний райтер із досвідом розробки. Ти пишеш для людини, яка **вперше**
бачить цей модуль і має ним скористатись, не відкриваючи реалізацію.

## Мета

Задокументувати публічний API модуля: контракт, інваріанти, помилки й межі.

## Контекст

- Модуль: `app/src/quote.ts`
- Аудиторія: розробник агенції, який підключає розрахунок кошторису в іншому
  проєкті. TypeScript знає, доменну логіку кошторисів — ні.
- Формат JSDoc уже частково є — доповнюй його, а не вигадуй свій.
- Тести `app/src/quote.test.ts` — джерело правди про поведінку. Якщо код і тест
  розходяться, правда в тесті.

## Обмеження

- НЕ змінюй виконуваний код. Тільки коментарі/JSDoc і `docs/`.
- НЕ описуй *як* працює реалізація — описуй *що* гарантує контракт.
  «Використовує метод найбільшого залишку» — деталь реалізації, вона зміниться.
  «Сума елементів дорівнює вхідній сумі» — контракт, він не зміниться.
- НЕ вигадуй поведінку, якої немає в коді чи тестах. Не знаєш — напиши
  «не визначено».
- Без маркетингових формулювань («потужний», «гнучкий»).

## Acceptance criteria

- [ ] Кожна експортована сутність має: призначення, параметри з одиницями
      вимірювання, що повертає, які помилки кидає і за яких умов.
- [ ] Для кожної функції явно виписано **інваріант** — твердження, яке істинне
      завжди (напр. «сума платежів == totalCents»).
- [ ] Є мінімум один приклад виклику з **конкретними числами** і результатом,
      який реально відповідає поведінці коду.
- [ ] Явно названо, що **не визначено** контрактом (напр. напрямок округлення).
- [ ] `cd app && npm run typecheck` і `npm test` — без змін у результаті.

## Формат відповіді

1. JSDoc-діф для `app/src/quote.ts`.
2. Окремо — таблиця «функція | інваріант | кидає» для вставки в `docs/`.

## Stop

Після документації зупинись. Побачив дефект — **опиши його в кінці окремим
списком**, але не виправляй: фікс іде через `prompts/debug-failing-test.md`.

## Слід запуску (2026-09-13, Claude Opus 5)

Прогін на `app/src/quote.ts` після фіксу. Що реально потрапило в код — JSDoc
з `@throws`, `@example splitInstallments(100, 3) // [34, 33, 33]` і формулювання
інваріанту словами «гроші не зникають і не з'являються».

Підсумкова таблиця контракту:

| Функція | Інваріант | Кидає `QuoteInputError` |
|---|---|---|
| `estimateTotalCents` | результат — ціле число центів ≥ 0 | `hours < 0`, `rateCents < 0`, `discountPercent` поза 0..100, нескінченні значення |
| `splitInstallments` | `result.length === parts`; `sum(result) === totalCents`; `max − min ≤ 1` | `totalCents` не ціле, `parts` не ціле або `≤ 0` |
| `formatMoney` | рядок виду `[-]$X,XXX.XX` | `cents` не ціле |

**Не визначено контрактом** (виписано явно, бо це реальна пастка):
напрямок округлення в `estimateTotalCents` при дробових `hours`; порядок, у
якому розподіляються «зайві» центи в `splitInstallments` (зараз перші платежі —
але це реалізація, не обіцянка); поведінка на `totalCents < 0`.

**Що спрацювало в промпті.** Обмеження «описуй контракт, а не реалізацію» дало
конкретну користь: перша чернетка JSDoc починалася з «розподіляє залишок
методом найбільшого залишку» — тобто документувала алгоритм, який завтра можна
змінити, не ламаючи жодного тесту. Після переформулювання в JSDoc лишився
інваріант суми, а назва алгоритму пішла в пояснювальний коментар нижче.

**Stop-правило теж спрацювало не даремно:** під час документування стало видно,
що порядок розподілу залишку зафіксовано тестом `платежі відрізняються не
більше ніж на 1 цент`, але не зафіксовано в контракті. Це знахідка, а не баг —
і за stop-правилом вона пішла в список наприкінці, а не в код.
