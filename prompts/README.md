# Prompt cookbook

Бібліотека перевірених промптів команди. Кожен промпт — окремий файл за
структурою [`_template.md`](./_template.md), перевірений на реальній задачі
(ціль за замовчуванням — `app/`).

## Індекс

| Промпт | Що робить | Перевірено на |
|---|---|---|
| [`review-pr.md`](./review-pr.md) | Рев'ю дифу перед мержем (приклад-планка з starter-репо) | `app/src/quote.ts` |
| [`add-tests.md`](./add-tests.md) 🔀 | Інваріантні тести на модуль — такі, що падають на реальних дефектах | `app/src/quote.ts` — знайшов дефект `splitInstallments` (8 червоних тестів) |
| [`debug-failing-test.md`](./debug-failing-test.md) | Довести червоний тест до кореневої причини й полагодити код, а не тест | ті самі 8 червоних → 24/24 зелених, тести не змінювались |
| [`review-security.md`](./review-security.md) | Безпекове рев'ю дифу перед комітом: секрети, exfil, зміни поза scope | діф Task A — знайшов ненавмисну зміну `package-lock.json`; контрольний прогін на exfil-рядку |
| [`document-module.md`](./document-module.md) | Описати публічний API: контракт та інваріанти, а не реалізацію | `app/src/quote.ts` — JSDoc з `@throws`/`@example` + розділ «не визначено контрактом» |
| [`refactor-safe.md`](./refactor-safe.md) | Перебудувати код без зміни поведінки, з доказом через незмінені тести | `app/src/quote.ts` — 7 throw-сайтів → 5, тести не чіпались |
| [`sanitize-client-doc.md`](./sanitize-client-doc.md) 🔀 | Підготувати клієнтський документ до передачі в модель | `materials/client-brief.md` → [`docs/sanitized-brief.md`](../docs/sanitized-brief.md) |

🔀 — промпт існує у двох діалектах (markdown + XML) з розбором, чи є різниця.

### Як вони пов'язані

Промпти не самостійні — між ними є порядок, і його варто тримати явним:

```
add-tests ──► debug-failing-test ──► refactor-safe ──► review-security ──► review-pr
   │                                      ▲
   └──── покриття, без якого ─────────────┘
         рефакторинг небезпечний
```

`refactor-safe` доводить безпеку через «тести зелені й не змінені» — тобто
рівно настільки, наскільки повне покриття. Тому він іде **після** `add-tests`,
а не замість нього.

`sanitize-client-doc` стоїть окремо: він виконується **до** будь-якої роботи з
клієнтським документом і має власне правило доступу (див.
[`docs/sanitization-checklist.md`](../docs/sanitization-checklist.md)).

### Що показали прогони

- **Acceptance criteria має бути предикатом, а не темою.** «Покрий крайові
  випадки» дефект не знаходить — під це підходить і зелений тест на довжину
  масиву. `sum(splitInstallments(total, parts)) === total` знаходить із першого разу.
- **Критерій, який можна перевірити командою, сильніший за критерій на слово.**
  `git diff --stat app/src/quote.test.ts` — порожній ⇒ тести не підганяли.
- **Stop-правило працює там, де обмеження не працює.** «Не чіпай код» у
  розділі «Обмеження» агент двічі трактував як побажання; те саме як
  stop-правило з вказівкою на наступний промпт — тримало.
- **Питання «чому це взагалі тут?» ловить більше, ніж чорний список патернів.**
  Це справедливо і для безпекового рев'ю, і для захисту від ін'єкцій
  (див. [`docs/injection-report.md`](../docs/injection-report.md)).

## Правила цієї бібліотеки

1. Один промпт — одна задача. Якщо в описі є «і ще», це два промпти.
2. Кожен промпт має **acceptance criteria**, які можна перевірити «так/ні».
3. Кожен промпт має **stop-правило** — де агент зупиняється.
4. Промпт без перевірки на реальній задачі у бібліотеку не потрапляє.
5. Змінюєте промпт — піднімайте `version` і пишіть, що саме змінилось.
