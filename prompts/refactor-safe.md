# Безпечний рефакторинг

## Роль

Розробник, який змінює структуру коду під наглядом тестів. Для тебе рефакторинг —
це зміна, після якої **жоден тест не змінився і жоден не впав**. Якщо довелось
правити тест, це вже не рефакторинг, а зміна поведінки.

## Мета

Прибрати названу проблему структури, зберігши зовнішню поведінку незмінною.

## Контекст

- Файл: `app/src/quote.ts`
- Проблема, яку прибираємо: `<вписати конкретно — напр. «валідація входу
  продубльована в трьох функціях»>`
- Тести-страховка: `app/src/quote.test.ts`, запуск `cd app && npm test`
- Публічний API модуля (**не міняти**): `estimateTotalCents`, `splitInstallments`,
  `formatMoney`, `QuoteInput`, `QuoteInputError`
- Модуль імпортується ззовні, тому зміна сигнатур — breaking change.

## Обмеження

- НЕ змінюй `app/src/quote.test.ts` — жодного рядка.
- НЕ змінюй експортовані імена, сигнатури й типи помилок.
- НЕ додавай функціональності «заодно» і не виправляй знайдені баги —
  рефакторинг і фікс не змішуються в одній зміні.
- НЕ додавай залежностей.
- Якщо для рефакторингу треба змінити поведінку — **зупинись і скажи**.

## Acceptance criteria

- [ ] `cd app && npm test` — зелений **до** і **після**, з тією ж кількістю тестів.
- [ ] `git diff --stat app/src/quote.test.ts` — порожній.
- [ ] `cd app && npm run typecheck` — без помилок.
- [ ] Названо конкретно, що стало краще, у вимірюваних термінах
      (мінус N дублювань / мінус N рядків / одне місце замість трьох).
- [ ] Явно сказано, які **ризики** несе зміна і що саме її страхує.

## Формат відповіді

1. План рефакторингу списком — **до** будь-яких змін.
2. Діф.
3. Вивід `npm test` до і після + `git diff --stat` по тестах.

## Stop

Зупинись після зеленого прогону. Не продовжуй на інші файли й не починай
«наступний очевидний крок» — кожен рефакторинг окремою зміною.

## Слід запуску (2026-09-13, Claude Opus 5)

**Проблема на вході** (вписана в «Контекст» замість плейсхолдера): після фіксу
Task A у `quote.ts` було 7 окремих `throw new QuoteInputError(...)`, з них
6 — руками зібрані повідомлення для трьох однакових за змістом перевірок
(«скінченне», «не від'ємне», «ціле»), розкиданих по трьох функціях.

**План, який агент видав до змін:** винести `assertNonNegative(value, name)` і
`assertInteger(value, name)` поряд із наявним `assertFinite`; доменні перевірки
(діапазон `discountPercent` 0..100, умова `parts > 0`) лишити на місцях — вони
різні за змістом і зведення їх в один хелпер тільки заплутає.

**Результат (фактичний вивід):**

```
Tests  24 passed (24)      ← до і після, та сама кількість
tsc --noEmit               ← exit 0
git diff --stat src/quote.test.ts   ← порожньо
throw new QuoteInputError: 7 → 5
```

Дублювання перевірки на ціле число: 3 місця → 1 хелпер. Дублювання перевірки
на від'ємність: 2 місця → 1 хелпер.

**Де промпт зупинив агента — і це головне.** Природний «наступний очевидний
крок» тут — звести всю валідацію `estimateTotalCents` в одну
`validateQuoteInput(input)`. Виглядає чистіше, але це вже зміна поведінки:
зараз `hours` перевіряється **до** `discountPercent`, і порядок помилок став би
іншим. Обмеження «якщо для рефакторингу треба змінити поведінку — зупинись і
скажи» + stop-правило «не починай наступний очевидний крок» закрили цей шлях.

**Ризик зміни й що його страхує:** хелпери тепер спільні, тож помилка в
`assertInteger` зламає `splitInstallments` і `formatMoney` одночасно. Страхує
це те, що кожна з функцій має власний тест на некоректний вхід — регресія
впаде у двох місцях, а не пройде мовчки.

**Чого промпту бракує (чесно).** Acceptance criteria перевіряють, що тести
зелені й не змінені — але «тести не змінились» гарантує збереження лише
**покритої** поведінки. Порядок валідацій вище тестом не покритий: якби агент
таки зробив `validateQuoteInput`, усі 24 тести лишились би зеленими, а
поведінка змінилася б. Тобто цей промпт безпечний рівно настільки, наскільки
повне покриття — і тому в cookbook він іде **після** `add-tests.md`, а не
замість нього. Це залежність між промптами, і її варто тримати явною.
