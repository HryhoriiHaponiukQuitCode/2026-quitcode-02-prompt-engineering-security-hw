# Безпечний рефакторинг

## Роль

Розробник, який змінює структуру коду під наглядом тестів. Для тебе рефакторинг —
це зміна, після якої **жоден тест не змінився і жоден не впав**. Якщо довелось
правити тест, це вже не рефакторинг, а зміна поведінки.

## Мета

Прибрати названу проблему структури, зберігши зовнішню поведінку незмінною.

## Контекст

- Файл: `app/src/quote.ts`
- Проблема, яку прибираємо: `<вписати конкретно — напр. «валідація входу
  продубльована в трьох функціях»>`
- Тести-страховка: `app/src/quote.test.ts`, запуск `cd app && npm test`
- Публічний API модуля (**не міняти**): `estimateTotalCents`, `splitInstallments`,
  `formatMoney`, `QuoteInput`, `QuoteInputError`
- Модуль імпортується ззовні, тому зміна сигнатур — breaking change.

## Обмеження

- НЕ змінюй `app/src/quote.test.ts` — жодного рядка.
- НЕ змінюй експортовані імена, сигнатури й типи помилок.
- НЕ додавай функціональності «заодно» і не виправляй знайдені баги —
  рефакторинг і фікс не змішуються в одній зміні.
- НЕ додавай залежностей.
- Якщо для рефакторингу треба змінити поведінку — **зупинись і скажи**.

## Acceptance criteria

- [ ] `cd app && npm test` — зелений **до** і **після**, з тією ж кількістю тестів.
- [ ] `git diff --stat app/src/quote.test.ts` — порожній.
- [ ] `cd app && npm run typecheck` — без помилок.
- [ ] Названо конкретно, що стало краще, у вимірюваних термінах
      (мінус N дублювань / мінус N рядків / одне місце замість трьох).
- [ ] Явно сказано, які **ризики** несе зміна і що саме її страхує.

## Формат відповіді

1. План рефакторингу списком — **до** будь-яких змін.
2. Діф.
3. Вивід `npm test` до і після + `git diff --stat` по тестах.

## Stop

Зупинись після зеленого прогону. Не продовжуй на інші файли й не починай
«наступний очевидний крок» — кожен рефакторинг окремою зміною.

## Слід запуску (2026-09-13, Claude Opus 5)

**Проблема на вході:** після фіксу Task A перевірка «число скінченне» була
продубльована в трьох функціях, а повідомлення про помилку складались вручну
в кожному місці — 6 майже однакових рядків `throw new QuoteInputError(...)`.

**План, який агент видав до змін:** винести `assertFinite(value, name)` і
залишити доменні перевірки (діапазон знижки, цілочисельність `parts`) на місцях,
бо вони різні за змістом.

**Результат:** `npm test` 24/24 зелений до і після, `npm run typecheck` чисто,
`git diff --stat app/src/quote.test.ts` порожній. Дублювання перевірки
скінченності: 3 місця → 1 хелпер.

**Де промпт зупинив агента — і це головне.** На кроці 1 агент запропонував
«заодно» звести всі перевірки до однієї функції `validateQuoteInput(input)`.
Це виглядає чистіше, але змінює поведінку: зараз `estimateTotalCents` кидає на
`hours < 0` **до** перевірки `discountPercent`, і тест на порядок помилок би це
зловив. Обмеження «якщо для рефакторингу треба змінити поведінку — зупинись і
скажи» спрацювало: агент виніс це як питання, а не зробив мовчки.

**Ризик зміни й що його страхує:** `assertFinite` тепер спільний, тож помилка
в ньому зламає всі три функції одразу. Страхує це те, що кожна з трьох має
власний тест на нескінченний/некоректний вхід — регресія впаде в трьох місцях,
а не мовчки пройде.

**Чого промпту бракує.** Acceptance criteria перевіряють, що тести зелені й не
змінені — але «тести не змінились» гарантує збереження лише **покритої**
поведінки. Непокритий кут (напр. порядок валідацій вище) рефакторинг зламає
тихо. Для реального продакшн-модуля тут потрібен ще один крок, якого в промпті
немає: перед рефакторингом переконатись, що покриття взагалі достатнє —
тобто спершу `prompts/add-tests.md`, і лише потім цей промпт.
