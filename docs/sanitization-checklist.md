# Чек-ліст санітизації даних для роботи з AI

Робочий документ команди. Проходити **перед** тим, як документ клієнта
потрапить у будь-яку модель — включно з тією, що всередині IDE.

## 1. Світлофор: що шукаємо

| Категорія | Приклади з наших проєктів | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, bot-токени, PAT, connection strings, вміст n8n credentials | нікуди; лише через env на рантаймі |
| 🔴 PII клієнтів і їхніх замовників | ПІБ, email, телефон, адреса, нікнейм у месенджері | нікуди в публічну модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи із замовленнями, скріншоти CRM | нікуди; замінити синтетикою |
| 🟡 Внутрішня комерція | маржа, собівартість години, умови угоди, конкуренти | лише enterprise / no-train |
| 🟡 Внутрішня логіка | схеми БД, назви внутрішніх сервісів, гілки | лише enterprise / no-train |
| 🟢 Постановка задачі | опис проблеми, критерії приймання, обсяги без даних | будь-яка модель |

## 2. Як маскуємо

- **redaction** — прибрати повністю: `<REMOVED>`, `<INTERNAL>`
- **masking** — лишити форму, прибрати значення: `+380 (XX) XXX-XX-XX`, `****-1234`
- **synthetic** — замінити правдоподібним вигаданим: `[CLIENT_1]`, `orders@example.test`
- **out-of-band** — секрет не потрапляє в текст узагалі: `<SECRET_OUT_OF_BAND>`
  плюс ім'я env-змінної, яку читатиме код

**Правило балансу:** після маскування задача має лишатись зрозумілою. Якщо модель
більше не розуміє, що робити, — замасковано зайве. Якщо збережено поле лише
«щоб було» — замасковано замало.

## 3. Перед тим, як вставити в модель

- [ ] Пошук по документу: `key`, `token`, `secret`, `password`, `pat`, `@`, `+380`
- [ ] Connection strings усіх видів: `postgres://`, `mysql://`, `mongodb+srv://`,
      `redis://`, `amqp://`
- [ ] Заголовки й ключі: `Authorization:`, `Bearer `, `-----BEGIN` (PEM),
      `AKIA` (AWS), `xoxb-` / `xoxp-` (Slack), `ghp_` / `github_pat_`
- [ ] Пошук не замінює перегляд очима: пройдіть документ ще раз вручну —
      найчастіше витікає те, що не має характерного префікса (адреси, суми,
      прізвища у вкладеннях і скріншотах)
- [ ] Жодного справжнього ПІБ / email / телефону / адреси
- [ ] Вигрузки замінені синтетичними рядками **того самого формату**
- [ ] Секрети — лише як імена env-змінних
- [ ] Скріншоти перевірені окремо (на них PII видно найчастіше)
- [ ] Назва файлу теж не містить назви клієнта
- [ ] Обраний інструмент відповідає **найвищій** категорії, що лишилась у документі

## 4. Категорія → інструмент

| Категорія | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | звичайна підписка (Claude Code / Cursor) | немає чутливого вмісту |
| 🟡 | enterprise-план з no-train політикою; за потреби — локальна модель | дані не мають потрапити в навчання |
| 🔴 | AI не використовуємо; або лише після санітизації до 🟢/🟡 | ризик не покривається жодним планом |

## 5. Окремо про креденшели інтеграцій

Те, що зараз лежить у n8n credentials, — найризикованіша категорія при переході
в код: у платформі воно сховане, у репозиторії — ні.

- ключі живуть у `.env` (у `.gitignore`) або в менеджері секретів;
- у коді й промптах фігурує лише **ім'я змінної**;
- у документах для моделі — `<SECRET_OUT_OF_BAND>`;
- ротація після кожного випадку, коли ключ міг потрапити в контекст.

## 6. Якщо секрет усе ж потрапив у модель

1. Вважати скомпрометованим — незалежно від політики вендора.
2. Ротувати ключ негайно.
3. Зафіксувати інцидент: що, куди, коли, хто.
4. Перевірити, чи не пішло воно ще й у git-історію (`git log -S`).
