## Задача

Клієнт вручну обробляє заявки на перевезення: менеджер копіює дані з пошти в
таблицю, потім створює запис у CRM і повідомляє водія в корпоративному
месенджері. Треба автоматизувати ланцюжок:

```
заявка → валідація → запис у CRM → сповіщення водія
```

**Обсяг:** ~400 заявок/тиждень, пікові дні — понеділок і четвер.

### Критерії приймання

- заявка з некоректним телефоном або без адреси доставки **не потрапляє в CRM**;
- сповіщення водію йде **не пізніше ніж за 2 хвилини** після заявки;
- усі відхилені заявки видно в **окремому звіті**.

## Вердикт

**ЗАДАЧА ЗБЕРЕЖЕНА: так.**

Перевірка за acceptance criteria промпту:

- пошук за `key|token|secret|password|postgres://|sk-|xoxb-|pat[A-Z]|\+380 \(\d` —
  жодного реального значення;
- усі 3 критерії приймання присутні дослівно;
- обсяг (400/тиждень), пікові дні, ланцюжок кроків — на місці;
- формат заявки збережено з поясненням, **чому** кожна особливість важлива для
  валідації (різні типи замовників, нестабільна структура адреси, нормалізація
  телефону);
- кількість і тип інтеграцій названо без самих доступів — оцінка обсягу робіт
  можлива.

### Чого бракує і що варто знати виконавцю

1. **Профіль клієнта довелось додати вручну.** Прибравши назву компанії, ми
   прибрали й контекст «логістика, B2B, ~30 людей», який впливає на оцінку.
   Санітизація без компенсації робить бриф біднішим за оригінал — це той самий
   ризик «замаскували під нуль». Тому профіль вписано окремим абзацем.
2. **Рядок про конкурента — найцікавіший випадок.** Він не містить ні секрету,
   ні PII, ні продакшн-даних. За світлофором це 🟢. Але це переговорна позиція
   агенції, і в зовнішній моделі їй не місце. **Жоден пошук за патернами такого
   не знайде** — тут спрацювало лише людське рішення. Звідси окремий пункт у
   чек-лісті: «чи є тут те, чого ви не сказали б клієнту вголос».
3. **Знахідка, якої не було в шаблонному списку категорій.** Критерій «пошук
   за `@`» дав спрацьовок на рядку з **особистим месенджером** контактної
   особи — це не email, тож у переліку «ПІБ / email / телефон / адреса» такої
   категорії немає. Критерій, сформульований як **пошуковий патерн**, знайшов
   те, чого не було в переліку категорій.
4. **Чек-ліст спіймав помилку в цьому ж документі.** Перший варіант цього
   розділу **цитував сам хендл** — тобто пояснення про те, як добре ми його
   замаскували, містило замаскований хендл у відкритому вигляді. Спрацював
   прогін acceptance criteria по **готовому результату**, а не по оригіналу.
   Звідси правило, яке пішло в чек-ліст: прогнати пошук по **вихідному**
   документі теж, включно з розділом «що ми замаскували» — саме там значення
   найчастіше й виживають.
5. **Важливе обмеження цього документа.** Його підготував локальний агент,
   який прочитав оригінал — тобто оригінал побував у контексті моделі. Для
   навчальних синтетичних даних це нормально. Для справжнього брифу
   «локальний агент» **не дорівнює** «нікуди не пішло»: Claude Code і Cursor
   надсилають контекст у хмару провайдера. Реальний порядок дій для 🔴-документа —
   маскування детермінованим скриптом **до** того, як файл потрапить у контекст;
   агент і промпт — це друга пара очей, а не перша лінія.
